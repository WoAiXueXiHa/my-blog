# 深入理解 Go GC：从可达性分析到混合写屏障

程序运行时会不断申请内存。如果已经不再使用的内存始终得不到释放，进程占用的内存就会持续增长，最终可能耗尽系统资源。

GC 全称 **Garbage Collection（垃圾回收）**。它负责自动识别已经无法被程序访问的对象，并回收这些对象占用的内存。

本文从内存管理的基本问题出发，依次介绍常见垃圾回收算法、三色标记、写屏障，以及 Go 一轮 GC 的完整运行过程。

## 1. 为什么需要 GC？

理解 GC 之前，可以先简单区分栈和堆：

- **栈**：主要保存函数调用帧、局部变量和参数等内容，随着函数调用和返回自动管理。
- **堆**：主要保存需要超出当前函数栈帧继续存活，或者编译器无法证明可以安全放在栈上的对象。

在 Go 中，变量最终分配在栈还是堆上，由编译器的**逃逸分析**决定，而不是由开发者直接指定。

先看一个 C 语言示例：

```c
int* func(void) {
    int a = 10;
    return &a;
}
```

`a` 位于 `func` 的栈帧中。函数返回后，栈帧被销毁，`&a` 也就不再是一个可以安全使用的地址。继续访问它属于未定义行为，这类指针通常称为悬挂指针。

Go 中看起来相似的代码却是安全的：

```go
func f() *int {
    a := 10
    return &a
}
```

Go 编译器会分析 `a` 的生命周期。**如果它必须在函数返回后继续存在，编译器通常会让它逃逸到堆上，之后由运行时负责管理。**

如果完全依赖开发者手动管理动态内存，很容易出现以下问题：

- 忘记释放，造成内存泄漏；
- 重复释放，导致程序异常；
- 释放后继续访问，产生悬挂指针。

C++ 提供了 `unique_ptr`、`shared_ptr` 和 `weak_ptr` 等智能指针来辅助管理资源。Go 则由运行时提供 GC，自动回收已经无法访问的堆对象。

需要注意，**GC 管理的是内存的可达性和生命周期。**文件描述符、网络连接等资源通常仍应通过 `Close` 等方法主动释放，不能依赖 GC 的执行时机。

## 2. GC 如何判断对象是否存活？

GC 不会判断“业务以后还想不想使用这个对象”，它真正判断的是：

> **从 GC Root 出发，是否还存在一条引用路径可以到达这个对象？**

例如：

```text
GC Root
   │
   ▼
   A ──▶ B ──▶ C

   D
```

从 Root 出发可以找到 A、B、C，因此它们都是可达对象。D 无法从任何 Root 到达，因此可以被回收。

常见的 GC Root 来源包括：

- 全局变量中的指针；
- goroutine 栈中的有效指针；
- runtime 维护的部分堆外数据结构中的指针。

扫描 goroutine 栈，是为了找出栈中有哪些指针正在指向堆对象，不是为了通过 GC 回收栈空间。

### 2.1 可达对象也可能造成内存泄漏

只要对象仍然可达，GC 就不能回收它，即使业务已经不再需要它：

```text
业务已经不再使用对象
        │
        ▼
全局 map、slice 或缓存仍然保存引用
        │
        ▼
对象仍然可以从 Root 到达
        │
        ▼
GC 无法回收
```

因此，带 GC 的语言仍然可能出现内存泄漏。**这里的泄漏通常不是“彻底丢失了内存地址”，而是“无用对象仍然被引用”。**

## 3. 常见的垃圾回收算法

### 3.1 引用计数

引用计数为每个对象记录当前存在多少个强引用。当计数变成 0 时，对象就可以立即回收。

C++ 的 `shared_ptr` 使用了引用计数思想，计数通常保存在独立的控制块中。它属于自动资源管理机制，但不能简单等同于完整的追踪式 GC。

优点：

- 引用数归零后可以及时回收；
- 原理简单直观。

缺点：

- 增加和删除引用时都需要维护计数；
- 无法天然解决循环引用。

如果 A 引用 B，B 又引用 A，即使外部已经不再使用它们，二者都说你先放手我再防守，结果就是僵持下去，无法释放。C++ 中可以使用 `weak_ptr` 打破不必要的强引用环。

### 3.2 标记清除

标记清除（Mark-Sweep）分为两个阶段：

1. **标记**：从 GC Root 出发，遍历并标记所有可达对象。
2. **清除**：检查堆中的对象，回收没有被标记的对象。

![标记清除过程](https://gitee.com/binary-whispers/pic/raw/master///20260910095744785.png)

标记清除能够处理循环引用，也不需要移动存活对象。不过，扫描和清扫堆需要一定成本，而且不移动对象可能造成内存碎片。

### 3.3 复制

经典复制算法将内存划分为两个区域，每次主要使用其中一个区域。当前区域需要回收时，将存活对象复制到另一个区域，然后整体释放原区域。

![复制算法](https://gitee.com/binary-whispers/pic/raw/master///20260910100548453.png)

优点：

- 存活对象排列紧凑，不容易产生内存碎片；
- 空闲区域可以通过移动分配指针快速分配。

缺点：

- 经典半区复制需要预留另一块内存，空间利用率较低；
- 存活对象较多时，复制成本较高；
- 对象移动后必须更新相关引用。

### 3.4 标记整理

标记整理（Mark-Compact）先标记存活对象，再将它们向内存区域的一端移动，使其连续排列，并更新所有相关引用。整理完成后，另一端会形成连续的空闲空间。

优点：

- 可以减少内存碎片；
- 整理后能够得到连续的空闲空间。

缺点：

- 需要移动对象并更新引用；
- 存活对象较多时，整理成本较高。

## 4. Go GC 的核心特点

当前 Go GC 可以概括为：

> **并发、精确、非分代、非移动的标记—清扫 GC。**

- **并发**：主要标记和清扫工作可以与用户 goroutine 同时执行。
- **精确**：运行时能够识别哪些内存位置保存了指针。
- **非分代**：不会按照对象年龄划分新生代和老年代。
- **非移动**：通常不会通过搬迁存活对象来整理堆。
- **标记—清扫**：先找出所有可达对象，再清扫不可达对象占用的槽位。

并发不等于完全没有暂停。为了安全地切换 GC 阶段，Go 仍然需要短暂的 STW。

STW 全称 **Stop The World**，表示暂时停止用户 goroutine 的执行。Go GC 的目标不是彻底消除 STW，而是将必须暂停的工作控制在较短时间内。

## 5. 三色标记

三色标记不是给对象真正染色，而是用白、灰、黑三种状态描述标记进度：

- **白色**：尚未被发现，目前还不知道它是否可达。
- **灰色**：已经确认可达，但它内部保存的指针还没有扫描完成。
- **黑色**：已经确认可达，而且它内部保存的指针也已经扫描完成。

白色不等于垃圾。只有标记阶段结束后仍然保持白色的对象，才会被视为不可达。

### 5.1 标记过程

1. 标记开始时，堆对象都视为白色。
2. 扫描 GC Root，将直接发现的堆对象标记为灰色，加入待处理队列。
3. 从队列中取出一个灰色对象，扫描它内部的指针。
4. 如果发现新的白色对象，就将其标灰并加入队列。
5. 当前灰色对象扫描完成后，将它标记为黑色。
6. 重复上述过程，直到不存在 Root 扫描任务和灰色对象。
7. 此时仍为白色的对象不可达，可以在清扫阶段回收。

![三色标记过程](https://gitee.com/binary-whispers/pic/raw/master///20260910111011155.png)

三色标记本质上仍然是一次从 Root 出发的可达性遍历：灰色代表“等待继续遍历”，黑色代表“已经遍历完成”。

Go 1.5 引入了以并发标记为核心的新 GC，大幅降低了全局暂停时间。但 GC 与用户 goroutine 并发执行，也带来了新的正确性问题。

## 6. 并发标记为什么可能漏标？

如果用户 goroutine 在标记期间修改指针，对象引用关系就会在 GC 扫描的同时发生变化。

出现漏标通常需要两个危险条件同时成立：

1. 已经扫描完成的黑色对象新增了对白色对象的引用；
2. 原来能够发现这个白色对象的灰色路径又被切断。

![并发标记中的引用变化](https://gitee.com/binary-whispers/pic/raw/master///20260910113103235.png)

此时，白色对象被藏到了已经扫描完成的黑色对象下方，而 GC 原本能够找到它的路径已经消失。由于黑色对象通常不会再次扫描，这个实际上仍然存活的对象就可能被遗漏。

写屏障正是用来解决这个问题的。

## 7. 写屏障

GC 写屏障（Write Barrier）和 CPU 内存屏障（Memory Barrier）不是同一个概念：

- CPU 内存屏障主要用于约束编译器和处理器的内存访问重排序；
- GC 写屏障是在程序写入指针时执行的一小段额外逻辑，用于维护并发标记的正确性。

可以把写屏障理解为：**当程序修改指针时，顺便通知 GC 保护相关对象，避免 GC 因引用关系变化而漏掉存活对象。**

### 7.1 强弱三色不变性

为了保证并发标记正确，可以约束标记期间对象颜色之间的关系。

**强三色不变性**要求：黑色对象不能直接指向白色对象。

![强三色不变性](https://gitee.com/binary-whispers/pic/raw/master///20260910113448112.png)

**弱三色不变性**允许黑色对象指向白色对象，但该白色对象必须仍然可以通过一条由白色对象组成的路径，被某个灰色对象发现。

![弱三色不变性](https://gitee.com/binary-whispers/pic/raw/master///20260910113646434.png)

两种不变性的目的相同：不能让仍然存活的白色对象同时失去所有尚待扫描的发现路径。

### 7.2 插入写屏障

插入写屏障关注即将写入的**新指针**。

如果程序准备建立 `A → B`，写屏障会先保护新指针指向的 B，再完成指针写入。这样可以避免已经扫描完成的黑色对象直接隐藏一个白色对象。

![插入写屏障](https://gitee.com/binary-whispers/pic/raw/master///20260910120906325.png)

它可以简化为：

```go
shade(newPtr)
slot = newPtr
```

其中，`shade` 表示保护相应对象：如果对象尚未标记，就将它加入后续的标记工作。

### 7.3 删除写屏障

删除写屏障关注即将被覆盖的**旧指针**。

假设 `slot` 原来指向 B，现在准备删除或覆盖这个引用。写屏障会先保护 B，再修改 `slot`，防止 GC 因原有路径消失而遗漏 B。

![删除写屏障](https://gitee.com/binary-whispers/pic/raw/master///20260910122702874.png)

它可以简化为：

```go
shade(oldPtr)
slot = newPtr
```

单独使用插入或删除写屏障，可能带来额外的栈重扫描或初始快照成本。Go 后来采用混合写屏障，将两种思路结合起来。

### 7.4 Go 的混合写屏障

Go 使用结合 Yuasa 删除屏障和 Dijkstra 插入屏障思想的混合写屏障。

假设：

```text
slot 原来保存 oldPtr
现在准备写入 newPtr
```

其概念模型可以简化为：

```text
shade(oldPtr)

如果当前 goroutine 的栈还没有完成扫描：
    shade(newPtr)

slot = newPtr
```

这两部分分别解决不同的问题：

- 保护 `oldPtr`，防止对象的唯一引用从堆上被移走后彻底隐藏；
- 在当前栈尚未完成扫描时保护 `newPtr`，防止对象从栈转移到已经扫描完成的黑色堆对象中。

实际实现可能为了降低同步和颜色判断成本而进行更保守的标记，但核心目的不变：不能让存活对象从 GC 的可达性遍历中消失。

需要特别区分栈扫描和堆对象标记：

- GC 会逐个扫描 goroutine 栈，找出其中指向堆对象的指针；
- 扫描某个栈时，只短暂暂停对应的 goroutine，完成后立即恢复；
- 对当前栈帧的普通指针写入通常不需要插入写屏障；
- 并发标记期间新分配的堆对象会直接标记为黑色。

![混合写屏障](https://gitee.com/binary-whispers/pic/raw/master///20260910203929479.png)

Go 1.8 引入混合写屏障，消除了标记结束时的全局栈重扫描，进一步缩短了 STW 时间。

## 8. 一轮 Go GC 如何运行？

一轮 Go GC 的主要过程可以分为清扫终止、并发标记、标记终止和并发清扫四个阶段。

### 8.1 清扫终止

新一轮 GC 开始时，运行时会短暂 STW，使各个 P 到达 GC 安全点。如果上一轮仍有未清扫的 span，还会先完成必要的遗留清扫。

随后，运行时会开启写屏障和分配辅助，并准备 Root 标记任务。所有 P 都启用写屏障后，才能安全地开始并发扫描。

可以将这一阶段理解为：**暂停片刻，为新一轮并发标记建立一致的起点。**

### 8.2 并发标记

恢复用户程序后，GC 与用户 goroutine 并发执行，主要完成以下工作：

- 扫描全局变量和 runtime 数据结构中的指针；
- 逐个扫描 goroutine 栈中的有效指针；
- 不断处理灰色对象，直到对象变成黑色；
- 通过写屏障保护标记期间发生的指针修改；
- 通过分配辅助，让内存分配较快的 goroutine 承担一部分标记工作。

扫描某个 goroutine 栈时，该 goroutine 会被短暂暂停，但不需要让全部 goroutine 在整个标记阶段一直停止。

当运行时确认已经没有 Root 标记任务和灰色对象时，就可以进入标记终止阶段。

### 8.3 标记终止

运行时再次短暂 STW，停止标记工作线程和分配辅助，刷新相关缓存并完成 GC 状态切换。

这一阶段的主要工作是收尾，而不是重新执行完整的 Root 扫描或重新标记整个堆。

### 8.4 并发清扫

标记结果确定后，用户程序恢复执行，写屏障关闭，运行时开始按 span 清扫未存活对象占用的槽位。

清扫既可以由后台 goroutine 并发完成，也可以在分配器需要新 span 时按需完成。清扫后的槽位会重新交给内存分配器使用。

对象槽位可以重新分配，并不代表对应的物理内存会立即归还操作系统。将空闲物理页归还操作系统，还涉及运行时的 scavenger 等机制。

## 9. Go GC 的触发与调节

Go GC 可以由堆增长、时间条件或主动调用触发。

### 9.1 堆增长触发

最主要的触发方式是堆增长。运行时的 GC 调步器会根据上轮存活堆内存、GC Root 扫描规模和 `GOGC`，计算下一轮 GC 的堆目标。

可以使用下面的近似公式理解：

$目标堆内存 ≈ 存活堆内存+（存活堆内存 + GC Roots）× GOGC / 100$

`GOGC` 默认值为 100。它可以粗略理解为允许内存在上轮存活规模的基础上继续增长一段距离，即进程内存严格翻倍。

调整 `GOGC` 本质上是在 CPU 开销和内存占用之间取舍：

- 提高 `GOGC`：GC 频率通常降低，CPU 开销减少，但峰值内存可能增加；
- 降低 `GOGC`：GC 频率通常提高，内存目标降低，但 CPU 开销可能增加。

可以通过 `GOGC` 环境变量或 `runtime/debug.SetGCPercent` 调整这个参数。

### 9.2 时间触发

如果较长时间没有发生 GC，系统监控线程会强制启动一轮。当前运行时默认的最长间隔约为两分钟。

时间触发可以避免分配量很小的程序长期不执行 GC。

### 9.3 主动触发

调用 `runtime.GC()` 可以主动发起一次 GC。该调用会阻塞当前调用者，直到本轮 GC 完成。

主动触发不代表整轮 GC 都处于 STW。它仍然会使用正常的并发 GC 流程，只是在必要阶段暂停用户 goroutine。

普通业务代码通常不需要频繁调用 `runtime.GC()`，运行时的自动调节一般能够做出更合适的决定。

## 10. 总结

Go GC 的核心是从 GC Root 出发进行可达性分析：能够到达的对象继续存活，无法到达的对象可以回收。

三色标记描述了遍历对象图的过程；混合写屏障保证用户 goroutine 修改指针时，不会让存活对象从并发标记中消失；短暂的 STW 则用于安全地切换 GC 阶段。

一轮 GC 主要经历：

```text
清扫终止（短暂 STW）
        │
        ▼
并发标记
        │
        ▼
标记终止（短暂 STW）
        │
        ▼
并发清扫
```

`GOGC`帮助运行时在 CPU 开销与内存占用之间取得平衡。
